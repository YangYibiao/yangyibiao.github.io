# 《高级程序设计（C++）》课程规划与案例设计（MiniBuild 主线版）

> 本版采用 MiniBuild 主线 + 每章辅助例子。17 周课件按本规划逐周迁移。

## 一、课程定位

- 授课对象：南京大学计算机学院大一本科生
- 先修课程：《程序设计基础》（C 语言）
- 教学安排：17 周 × 每周 2 学时，共 34 学时；每份课件对应一次课
- 课程目标：从“会写 C 程序”迈向“会用 C++ 做抽象设计与工程实现”

三条主线：

1. **抽象与边界**：类、接口、继承、多态、模块
2. **生命周期与资源**：构造/析构、拷贝/移动、RAII、智能指针、异常安全
3. **复用与并发**：模板、STL、Lambda、并发与同步、声明式与事件驱动

组织原则：**一条主线项目 + 每章一个最小辅助例子**，比例约 60% / 30% / 10%。每个辅助例子结束前明确回到主线：它在 MiniBuild 里对应哪一处。

## 二、主线项目：MiniBuild

### 2.1 项目定义

MiniBuild 是一个简化版构建工具（迷你 make）：

- 读取 `Buildfile` 中的“目标—依赖—命令”规则；
- 建立依赖 DAG，检测环和缺失依赖；
- 比较时间戳，判断哪些目标过期；
- 按拓扑序执行命令，支持 `-j N` 并行；
- 输出构建日志、错误上下文和事件；
- 支持 `clean`、`--dry-run`、`--graph` 等基本选项。

它不是重写 GNU make，而是一个几百行、可讲清、可测试的教学项目。

### 2.2 Buildfile 语法（第一版）

```text
# 注释
app: main.o util.o
    g++ main.o util.o -o app

main.o: main.cpp util.h
    g++ -c main.cpp

util.o: util.cpp util.h
    g++ -c util.cpp
```

第一版只支持：

- 一行一个目标，`目标: 依赖...`；
- 下一行缩进为命令（一个目标一条命令）；
- `#` 注释、空行；
- 默认目标为第一个目标，或显式 `all`。

变量、模式规则、通配符、多命令、`include` 作为后续扩展，不进入第一版。

### 2.3 最终形态

```text
minibuild/
├── include/
│   ├── target.h          # 目标与状态
│   ├── rule.h            # 规则接口与派生规则
│   ├── graph.h           # 依赖图、拓扑排序
│   ├── parser.h          # Buildfile 解析
│   ├── executor.h        # 命令执行与结果
│   ├── scheduler.h       # 串行/并行调度
│   └── event.h           # 构建事件与观察者
├── src/
│   ├── target.cpp
│   ├── rule.cpp
│   ├── graph.cpp
│   ├── parser.cpp
│   ├── executor.cpp
│   ├── scheduler.cpp
│   └── main.cpp
├── tests/
├── examples/hello/
├── Buildfile
├── CMakeLists.txt
└── README.md
```

### 2.4 CLI

```text
minibuild [target] [-j N] [--dry-run] [--clean] [--graph] [--verbose]
```

### 2.5 为什么选它

- 学生每天编译/构建，领域不陌生；
- DAG、拓扑排序天然属于 STL/算法；
- 并行构建天然属于线程、互斥量、条件变量；
- 构建日志/事件天然属于观察者、事件循环；
- 文件、命令、失败天然属于 RAII、I/O、异常；
- 命令行程序，不需要 GUI、数据库、网络，规模可控、容易评分；
- 名字不与知名 C++ 库冲突（不使用 TaskFlow 作为项目名）。

### 2.6 边界

- 不实现完整 GNU make 语法；
- 不要求跨平台 shell 兼容；
- 第一版命令可以用进程内 action 或 `std::system`，后期再扩展外部命令；
- 重点是设计、生命周期、依赖图、并发和错误处理，不是构建工具本身的功能数量。

## 四、每周课堂结构

1. **主线回顾（约 5 分钟）**：上周项目状态、本周要解决的问题。
2. **最小辅助例子（约 15 分钟）**：只讲本周一个机制，10–30 行代码。
3. **回到 MiniBuild（约 15 分钟）**：这个机制在项目中对应哪一处，现场重构/扩展。
4. **检查点与作业（约 5 分钟）**：本周项目应达到的可运行状态、测试和提交要求。

不要在每页贴完整项目代码。主线代码只在检查点展示完整版；平时用差异、片段或接口图。

## 七、评分建议

- **周检查点 30%**：每周可运行的小目标 + 简短说明。
- **阶段里程碑 30%**：第 6、11、15 周各一次，检查设计、测试和重构。
- **最终项目 30%**：功能、设计、测试、README、演示。
- **课堂/作业 10%**：辅助案例、小测、参与度。

建议最终演示包含：

```bash
minibuild --graph          # 打印依赖图
minibuild -j4              # 并行构建
minibuild --dry-run        # 只打印将执行的命令
minibuild clean            # 清理
```

## 八、与旧版 TaskFlow 的对应关系

| TaskFlow | MiniBuild |
| :-- | :-- |
| `Task` | `Target` / `Job` |
| `TaskList` | `Graph` / `TargetSet` |
| `TaskRunner` | `Scheduler` |
| `TaskRepository` | `Repository<T>` / `Buildfile` 解析 |
| 任务事件 | 构建事件 / 观察者 |
| 任务优先级 | 目标优先级 / 拓扑调度 |

现有辅助案例（`String`、`Buffer`、`Shape`、`Complex` 等）可以保留；需要替换的是主线案例的命名、需求和逐周增量。
