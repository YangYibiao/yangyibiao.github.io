本讲目标

能够把“怎么做”的循环改写成“做什么”的管道，并用回调/事件循环组织交互式程序。

两种编程范式

命令式（imperative）

  • 描述“怎么做”：步骤、状态变化

  • 循环、赋值、分支

  • 与冯·诺依曼结构一致

  • 代表：过程式、面向对象

int sum = 0;
for (int i = 1; i <= 3; ++i) {
    sum += i;
}

声明式（declarative）

  • 描述“做什么”：结果、关系

  • 不显式管理循环与状态

  • 更精炼，潜在并行性更强

  • 代表：函数式、逻辑式、SQL、Ranges

auto result = views::iota(1, 4)
            | views::filter(...)
            | views::transform(...);

两者不是互斥的：现代 C++ 在多范式之间切换，底层实现仍然是命令式，但接口可以是声明式。

函数式的五个特征

纯函数

  • 相同输入 → 相同输出

  • 不修改外部状态（无副作用）

  • 引用透明，便于推理与测试

无状态

  • 变量绑定后不再改变

  • 计算产生新数据，而不是修改旧数据

函数是值

  • 函数可以作为参数、返回值

  • 高阶函数：接受/返回函数

递归

  • 用递归替代循环

  • 尾递归可被优化为迭代

惰性求值

  • 需要结果时才计算

  • 可避免不必要的中间数据

工程价值

纯函数 + 不可变数据让并发更安全：没有共享可变状态，就不需要复杂的锁。

递归与尾递归

普通递归

int fib(int n) {
    if (n <= 2) return 1;
    return fib(n - 1) + fib(n - 2);
}

会重复计算，指数级时间；深递归可能栈溢出。

尾递归

int fib(int n, int a = 1, int b = 1) {
    if (n <= 2) return b;
    return fib(n - 1, b, a + b);
}
尾调用优化

递归调用是函数的最后一步，且结果不再参与其他运算；编译器可以复用当前栈帧，把递归转成循环。

C++ 标准不强制尾调用优化；GCC/Clang 在 -O2 下通常能优化简单的尾递归。不要把“依赖 TCO”当作可移植保证。

写法

把中间结果作为参数传入（累加器），让递归调用成为最后一步。

filter / map / reduce：数据处理三板斧

filter：筛选

保留满足条件的元素。

std::vector<int> evens;
std::copy_if(nums.begin(), nums.end(),
             std::back_inserter(evens),
             [](int x) { return x % 2 == 0; });

map：变换

对每个元素应用函数，产生新元素。

std::vector<int> doubled;
std::transform(evens.begin(), evens.end(),
               std::back_inserter(doubled),
               [](int x) { return x * 2; });

reduce：归约

把集合折叠成一个值。

int sum = std::accumulate(
    doubled.begin(), doubled.end(), 0);

filter → map → reduce 是最常见的数据流水线；大数据框架的 MapReduce 也源于同一思想。

用 Ranges 写管道 C++20 
#include <ranges>

std::vector<int> nums{1, 2, 3, 4, 5, 6};

auto result = nums
    | std::views::filter([](int x) {
          return x % 2 == 0;
      })
    | std::views::transform([](int x) {
          return x * 2;
      });

for (int x : result) {
    std::cout << x << ' ';   // 4 8 12
}
特点

  • 管道顺序即数据流顺序

  • 惰性求值：遍历时才计算

  • 不创建中间 vector

  • 可读性接近需求描述

生命周期 result 是视图，引用 nums；nums 销毁后视图悬空。不要返回指向局部容器的视图。
偏函数应用：固定部分参数 
void print(int n, int base);

// 固定 base = 10，生成单参数函数
auto print10 = [](int n) {
    print(n, 10);
};

print10(42);   // 等价于 print(42, 10);

更通用的 std::bind：

using namespace std::placeholders;
auto print10 = std::bind(print, _1, 10);
用途

  • 为通用函数生成专用版本

  • 减少重复传参

  • 作为算法谓词

  • 适配接口签名

现代写法

优先用 Lambda 而不是 std::bind：可读性更好，编译期优化更充分。

柯里化：把多参数拆成函数链 
int add(int x, int y) { return x + y; }

auto curried_add = [](int x) {
    return [x](int y) { return add(x, y); };
};

auto add5 = curried_add(5);
int a = add5(3);   // 8
int b = add5(10);  // 15

调用形式：curried_add(5)(3)

与偏函数应用的区别

  • 偏函数应用：固定部分参数，得到参数更少的函数

  • 柯里化：把 f(x,y,z) 变成 f(x)(y)(z)

  • 偏函数应用可以任意顺序绑定；柯里化按顺序逐个绑定

柯里化在纯函数式语言中很常见；C++ 中主要用于函数组合与延迟求值，不要为了“炫技”而过度使用。

逻辑式程序设计一瞥

Prolog 风格

path(a, b).
path(c, d).

path(X, Y) :- path(Y, X).
path(X, Y) :- path(X, Z), path(Z, Y).

?- path(m, n).

程序由事实和规则组成；提问后系统自动匹配、搜索、回溯。

特点

  • 数据（事实/规则）就是程序

  • 计算由推理引擎完成

  • 适合规则系统、专家系统、查询

  • 代表语言：Prolog、Datalog

与函数式对比

函数式描述“如何变换数据”，逻辑式描述“什么关系成立”；两者都属于声明式。

为什么需要事件驱动？

顺序程序

输入 → 计算 → 输出 → 结束

适合批处理，但无法应对“用户随时可能操作”的交互场景。

事件驱动

程序长期运行，等待事件：

  • 鼠标点击

  • 键盘输入

  • 定时器到期

  • 网络数据到达

  • 窗口重绘

事件发生后，调用注册的处理函数。

控制反转：不是主程序调用系统，而是系统在事件发生时调用你注册的函数。

事件循环与回调 
using Handler = std::function<void(const Event&)>;

class EventLoop {
public:
    void on(EventType type, Handler handler) {
        handlers_[type].push_back(std::move(handler));
    }

    void dispatch(const Event& e) {
        auto it = handlers_.find(e.type);
        if (it != handlers_.end()) {
            for (auto& h : it->second) {
                h(e);
            }
        }
    }
private:
    std::map<EventType, std::vector<Handler>> handlers_;
};
组成

  • 事件类型：标识“发生了什么”

  • 处理器表：每种事件对应一组回调

  • 分发：事件到达时依次调用

  • 事件循环：不断取事件、分发、等待

响应性

单个处理器不能执行太久，否则事件循环被阻塞，程序“假死”。耗时任务应交给工作线程或拆成小步骤。

观察者模式：对象之间的订阅 
class Subject {
public:
    void subscribe(std::function<void(int)> f) {
        observers_.push_back(std::move(f));
    }

    void notify(int value) {
        for (auto& f : observers_) {
            f(value);
        }
    }
private:
    std::vector<std::function<void(int)>> observers_;
};

Subject s;
s.subscribe([](int x) {
    std::cout << "observer: " << x << "\n";
});
s.notify(42);
模型

  • Subject：状态变化时通知观察者

  • Observer：注册回调，被动接收通知

  • 一对多、松耦合

  • GUI、事件总线、消息队列的基础

生命周期

观察者对象销毁前必须取消订阅，否则 Subject 持有悬空的回调（尤其是按引用捕获时）。用 weak_ptr 或显式 unsubscribe。

事件驱动 vs 顺序程序
维度 顺序程序 事件驱动
控制流 代码顺序决定 事件发生决定
主结构 循环、函数调用 事件循环 + 回调
适用 批处理、计算密集型 GUI、服务器、交互式
难点 算法与数据结构 状态管理、回调生命周期
响应性 长时间计算会阻塞 处理器短小、异步任务
本质

事件驱动把“什么时候执行”从代码顺序中解耦出来；代价是控制流分散，调试与状态追踪更困难。

主线案例：MiniBuild 的事件调度 
enum class EventType { Started, Finished, Failed };

struct Event {
    EventType type;
    int target_id;
};

EventLoop loop;

loop.on(EventType::Started, [](const Event& e) {
    std::cout << "target started: " << e.target_id << "\n";
});

loop.on(EventType::Finished, [](const Event& e) {
    std::cout << "target finished: " << e.target_id << "\n";
});

loop.dispatch({EventType::Started, 1});
loop.dispatch({EventType::Finished, 1});
设计点

  • 事件只携带必要数据（类型 + ID）

  • 处理器通过注册加入，不修改分发逻辑

  • 新增事件类型 → 新增枚举值与处理器

  • 分发循环保持稳定

与多态对比

多态用“对象类型”分派，事件驱动用“事件类型”分派；两者都能实现开闭原则，适用场景不同。

课堂任务 16：声明式任务统计
任务

给定 std::vector<Target> targets，用声明式风格完成：

  1. 过滤出未构建目标
  2. 提取名称
  3. 按名称排序
  4. 统计名称总长度
  5. 输出前 3 条

要求：

  • 优先使用 C++20 Ranges 管道

  • 如果环境不支持 Ranges，用 copy_if / transform / accumulate 组合

  • 不使用手写 for 循环完成筛选与变换

验收标准

  • 管道顺序清晰：filter → transform → sort

  • 不产生不必要的中间容器（Ranges 版本）

  • 结果与命令式版本一致

  • 代码可读性优于手写循环

  • 能解释惰性求值的时机

提示

Ranges 的 views::filter / views::transform 是惰性的；sort 需要具体容器，所以先 ranges::to<std::vector>（C++23）或手动收集。

任务 16 参考实现 
#include <algorithm>
#include <numeric>
#include <ranges>
#include <vector>

auto unbuilt = targets
    | std::views::filter([](const Target& t) {
          return !t.is_built();
      })
    | std::views::transform([](const Target& t) {
          return t.name();
      });

std::vector<std::string> names(
    unbuilt.begin(), unbuilt.end());

std::sort(names.begin(), names.end());

int total_len = std::accumulate(
    names.begin(), names.end(), 0,
    [](int acc, const std::string& s) {
        return acc + static_cast<int>(s.size());
    });

for (std::size_t i = 0;
     i < names.size() && i < 3; ++i) {
    std::cout << names[i] << "\n";
}
要点

  • filter + transform 组成惰性管道

  • 用迭代器区间构造 vector，物化结果

  • sort 需要随机访问迭代器

  • accumulate 做归约

  • 输出阶段允许索引循环

C++23 的 std::ranges::to<std::vector>() 可以省去手动构造；当前环境若只支持 C++20，用迭代器构造即可。

常见陷阱

声明式

  • 返回指向局部容器的视图 → 悬空

  • 惰性管道被遍历多次 → 重复计算

  • 为了“函数式”而写出难懂的柯里化

  • 忽略副作用：Lambda 修改外部变量

事件驱动

  • 回调按引用捕获局部变量，对象先销毁

  • 观察者忘记取消订阅

  • 处理器执行太久，阻塞事件循环

  • 回调中修改订阅列表，导致迭代器失效

  • 事件顺序与状态不一致

原则

声明式让“做什么”更清晰，事件驱动让“何时做”更灵活；两者都要求你明确数据与对象的生命周期。
