本讲目标

能够识别常见内存安全错误，并用 RAII + 智能指针把“谁负责释放”变成类型系统的一部分。

进程的内存分区
进程地址空间（示意，从高到低）
高地址栈 stack：局部变量、函数调用帧，自动增长/收缩
↓（空闲空间）
↑堆 heap：new / malloc 动态分配，手动管理
—全局/静态区：全局变量、静态成员
—常量区：字符串字面量、const 全局
低地址代码区：机器指令
生命周期

  • 栈对象：作用域结束自动销毁

  • 堆对象：delete 才销毁

  • 全局/静态：程序开始到结束

  • 字符串字面量：静态存储，只读

关键

“指针存在”不等于“对象还活着”。内存安全问题的核心，是访问了不该访问或已经失效的内存。

内存安全的定义
空间安全（spatial）

对象还活着，但访问范围错了：

  • 数组越界读/写

  • 解引用空指针

  • 访问未初始化内存

  • 类型混淆

时间安全（temporal）

对象已经失效，程序还在使用：

  • 释放后使用（UAF）

  • 重复释放（double free）

  • 悬空指针/引用

  • 内存泄漏

内存安全 = 程序只能访问它拥有的、仍然有效的、在边界内的内存。

这两类问题经常组合出现：越界写破坏堆管理信息，随后导致释放时崩溃。

真实世界：内存错误的代价

CrowdStrike 事件（2024）

  • 一次配置更新导致约 850 万台 Windows 设备蓝屏

  • 影响航空、银行、医院、酒店

  • 预计损失数十亿美元

OpenSSL Heartbleed（2014）

  • 心跳扩展缺少边界检查

  • 攻击者可读取服务器进程内存

  • 影响数百万 HTTPS 服务器

统计

  • 微软 MSRC：约 70% 的安全补丁针对内存安全问题

  • Chrome：高/严重漏洞中约 70% 与内存管理有关

  • C/C++ 赋予程序员直接控制内存的能力，也把责任交给了程序员

本讲的意义

内存安全不是“考试里的偏题”，而是工业界最昂贵的一类缺陷。现代 C++ 的方向是：让正确做法成为默认做法。

空间类问题一：数组越界 
int a[3] = {1, 2, 3};

a[3] = 42;        // 越界写：未定义行为
int x = a[10];    // 越界读：未定义行为

char buf[8];
std::strcpy(buf, "this is too long");  // 溢出
后果

  • 覆盖相邻变量

  • 破坏堆管理元数据

  • 读到敏感数据

  • 程序崩溃或“看起来正常”

为什么危险

越界写可能不会立刻崩溃，而是悄悄破坏别的数据；问题在很久之后才暴露，极难定位。

空间类问题二：空指针与未初始化 
int* p = nullptr;
*p = 42;              // 空指针解引用

int* q;               // 未初始化（野指针）
*q = 42;              // 指向随机地址

int x;                // 未初始化
if (x > 0) { ... }    // 读取未定义值
防御

  • 指针定义时初始化为 nullptr

  • 使用前检查非空

  • 变量定义时初始化

  • 用引用表达“必不为空”

  • 开启编译警告 -Wuninitialized

现代 C++ nullptr 代替 NULL / 0，避免与整数重载混淆；std::optional 表达“可能没有值”。
时间类问题一：释放后使用（UAF） 
int* p = new int(42);
delete p;

std::cout << *p;   // UAF：读取已释放内存
*p = 7;            // UAF：写入已释放内存

更隐蔽的版本：

Target* t = new Target(1, "A", 2);
delete t;
t->print();        // 对象已销毁，虚表指针可能已失效
为什么难发现

  • 释放后的内存可能还没被复用，读到的仍是旧值

  • 程序可能“正常运行”很久

  • 在多线程下时序变化，偶发崩溃

CWE-416

Use After Free 是浏览器、内核、字体解析器等的高危漏洞来源。

时间类问题二：重复释放与悬空指针 
int* p = new int(1);
delete p;
delete p;          // double free：未定义行为
int* p = new int(2);
int* q = p;
delete p;
*p = 3;            // p 悬空
*q = 4;            // q 也悬空
悬空指针的来源

  • delete 后未置空

  • 指向局部变量的指针逃逸出作用域

  • 容器扩容后旧迭代器/指针失效

  • 对象被移动后源对象被继续使用

习惯 delete p; 后立即 p = nullptr; 只能防止“再次 delete”，不能防止其他别名指针悬空；根本方案是明确所有权。
时间类问题三：内存泄漏 
void leak() {
    int* p = new int(10);
    // 忘记 delete
}

void early_return(bool bad) {
    Target* t = new Target(1, "A", 1);
    if (bad) return;   // 提前返回，泄漏
    delete t;
}

void exception_path() {
    Target* t = new Target(1, "A", 1);
    may_throw();       // 抛异常，delete 执行不到
    delete t;
}
泄漏的代价

  • 长时间运行的服务内存持续增长

  • 最终 OOM 或被系统杀死

  • 嵌入式/移动设备资源有限

最容易漏的路径

提前 return、异常、循环中的 continue / break。手动管理资源的代码，每条路径都要记得释放。

悬空指针：返回局部变量的地址 
int* bad() {
    int x = 5;
    return &x;     // 函数返回后 x 已销毁
}

int& bad_ref() {
    int x = 5;
    return x;      // 悬空引用
}

int main() {
    int* p = bad();
    std::cout << *p;   // 未定义行为
}
正确做法

  • 返回值（拷贝/移动）

  • 返回 std::unique_ptr / std::shared_ptr

  • 由调用方传入输出参数

  • 确保对象生命周期长于指针

编译器警告 -Wreturn-local-addr 能发现直接返回局部变量地址；但通过指针间接逃逸的情况仍需人工审查。
未定义行为：编译器可以做任何事

UB 不是“结果随机”

int a[3];
a[3] = 1;          // UB

int x;
if (x > 0) ...     // UB

int* p = nullptr;
*p = 1;            // UB

编译器可以假设 UB 不会发生，从而做出激进的优化。

常见后果

  • 删除整段“不可能执行”的代码

  • 循环被优化成死循环

  • 变量被寄存器缓存，读写顺序改变

  • 在不同编译器/优化级别下表现不同

重要

“在我的机器上能跑”不能证明程序正确。UB 的代码没有可依赖的语义。

防御体系：不要只靠“小心”
层次 手段 作用
编码规范 初始化、RAII、避免裸 new 从源头减少错误
静态分析 编译器警告、clang-tidy、Coverity 编译期发现问题
动态检测 ASan、UBSan、Valgrind 运行时捕获越界/UAF/泄漏
语言机制 智能指针、容器、std::span 让正确做法更容易
运行环境 沙箱、ASLR、硬件标签 限制漏洞影响
组合使用

没有任何单一手段能解决所有内存安全问题；工程上采用“预防 + 检测 + 隔离”的分层防御。

AddressSanitizer：让错误现场暴露 
g++ -std=c++17 -g \

./main

能发现什么

  • 堆/栈/全局越界

  • use-after-free

  • double-free

  • 内存泄漏（LeakSanitizer）

  • 未定义行为（UBSan）

使用建议

开发与测试阶段默认开启；性能测试和发布版本关闭。Sanitizer 报告要当作真实缺陷处理，不能忽略。

所有权：谁负责 delete？

裸指针的问题

Target* create();
void use(Target* t);
void destroy(Target* t);

仅看类型，无法知道：

  • 谁拥有对象？

  • 调用 use 后对象是否还有效？

  • 谁应该调用 destroy？

  • 能否复制这个指针？

所有权模型

  • 独占：同一时刻只有一个所有者 → unique_ptr

  • 共享：多个所有者共同延长生命周期 → shared_ptr

  • 观察：不拥有，只观察是否还活着 → weak_ptr / 裸指针 / 引用

目标

把“谁负责释放”从注释和口头约定，变成类型系统的一部分。

unique_ptr：独占所有权 
#include <memory>

auto p = std::make_unique<Target>(1, "main.o", 2);
p->build();
p->print();

// p 离开作用域时自动 delete
std::unique_ptr<Target> q(new Target(2, "util.o", 3));
// 不推荐直接 new；make_unique 更安全
特点

  • 同一时刻只有一个 unique_ptr 拥有对象

  • 不能拷贝，只能移动

  • 大小通常与裸指针相同

  • 析构时自动 delete

  • 支持多态：unique_ptr<Target> 可持有派生类对象

make_unique std::make_unique<T>(args...) 把分配与构造放在一个表达式里，避免裸指针短暂暴露。C++14 起可用。
移动所有权 
auto p = std::make_unique<Target>(1, "A", 1);

// auto q = p;              // 错误：不能拷贝
auto q = std::move(p);      // 所有权转移

if (!p) {
    std::cout << "p is empty\n";
}
std::unique_ptr<Target> make_target() {
    return std::make_unique<Target>(1, "A", 1);
}

auto t = make_target();   // 移动（或省略）
规则

  • 移动后源指针变为 nullptr

  • 不要继续解引用源指针

  • 函数返回 unique_ptr 表示“把所有权交给调用方”

  • 函数参数 unique_ptr<T> 表示“接管所有权”

  • 参数 T* / T& 表示“只借用，不拥有”

接口语义

看到 unique_ptr<T> 参数，调用方必须 std::move，这明确表达了“我把对象交给你了”。

unique_ptr 与容器、多态 
std::vector<std::unique_ptr<Target>> targets;

targets.push_back(
    std::make_unique<PrintTarget>("hello"));
targets.push_back(
    std::make_unique<CommandTarget>("g++ main.o -o app"));

for (const auto& t : targets) {
    t->run();          // 动态绑定
}
// 容器销毁时，每个 unique_ptr 自动 delete
为什么好用

  • 容器拥有元素，元素生命周期明确

  • 多态对象通过基类指针统一管理

  • 不需要手写析构循环

  • 不会误拷贝导致双重释放

前提

基类必须有虚析构函数，否则通过 unique_ptr<Target> 删除派生对象时，派生类析构不会执行。

shared_ptr：共享所有权 
auto a = std::make_shared<Target>(1, "A", 1);
auto b = a;              // 引用计数 2
auto c = b;              // 引用计数 3

std::cout << a.use_count();   // 3

b.reset();               // 引用计数 2
c.reset();               // 引用计数 1
// a 离开作用域 -> 计数 0 -> delete
引用计数

  • 每个对象关联一个控制块，记录 shared_ptr 数量

  • 拷贝 +1，析构/重置 -1

  • 计数归零时销毁对象

  • 多个线程各自持有/拷贝不同的 shared_ptr 实例（共享同一控制块）是安全的；并发读写同一个 shared_ptr 对象仍需同步

make_shared std::make_shared<T>(...) 一次分配对象 + 控制块，通常比 shared_ptr<T>(new T) 更高效。
shared_ptr 的经典错误 
int* raw = new int(5);

std::shared_ptr<int> a(raw);   // 计数 1
{
    std::shared_ptr<int> b(raw); // 另一个计数 1！
}                               // b 析构 -> delete raw

std::cout << *a;   // UAF
// a 析构 -> 再次 delete -> double free
规则

  • 不要用同一个裸指针构造多个 shared_ptr

  • 需要共享时，拷贝已有的 shared_ptr

  • 从函数返回 shared_ptr，而不是返回裸指针再包装

  • 优先 make_shared

本质

每个 shared_ptr 独立维护控制块；两个控制块都以为自己拥有对象，最终各自 delete 一次。

循环引用：引用计数不是万能 GC 
struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;   // 循环！
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;    // b 计数 2
b->prev = a;    // a 计数 2

a.reset();      // a 计数 1
b.reset();      // b 计数 1
// 两个对象互相引用，计数永远不为 0
问题

  • 对象已经不可达，但引用计数仍大于 0

  • 内存永远不释放

  • 链表、树、图、观察者模式中常见

修复

把其中一个方向改为 std::weak_ptr：观察者不增加引用计数，打破循环。

weak_ptr：只观察，不拥有 
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev;   // 不增加计数
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->prev = a;     // weak，不增加 a 的计数

std::weak_ptr<Node> w = a;
if (auto s = w.lock()) {   // 升级为 shared_ptr
    // 对象仍然存活
} else {
    // 对象已销毁
}
API

  • lock()：返回 shared_ptr，失败返回空

  • expired()：对象是否已销毁

  • use_count()：当前共享计数

  • reset()：放弃观察

所有权表达 shared_ptr 表示“我拥有”，weak_ptr 表示“我观察但不延长生命周期”。观察者模式、缓存、父子引用常用。
自定义删除器与数组 
// 文件指针：需要 fclose 而不是 delete
auto deleter = [](std::FILE* f) {
    if (f) std::fclose(f);
};
std::unique_ptr<std::FILE, decltype(deleter)>
    file(std::fopen("data.txt", "r"), deleter);

// 动态数组
std::unique_ptr<int[]> arr(new int[10]);
arr[0] = 42;
要点

  • unique_ptr<T, Deleter> 可以管理任意资源

  • 删除器是类型的一部分

  • 数组用 unique_ptr<T[]>，自动 delete[]

  • shared_ptr 也支持自定义删除器

大多数情况下不需要自定义删除器：文件用 std::fstream，锁用 std::lock_guard，容器用标准容器。

主线案例：用 unique_ptr 管理任务 
class TargetList {
public:
    void add(std::unique_ptr<Target> target) {
        targets_.push_back(std::move(target));
    }

    void run_all() const {
        for (const auto& t : targets_) {
            t->run();
        }
    }

    std::size_t size() const { return targets_.size(); }

private:
    std::vector<std::unique_ptr<Target>> targets_;
};

TargetList list;
list.add(std::make_unique<PrintTarget>("hello"));
list.add(std::make_unique<CommandTarget>("g++ main.o -o app"));
list.run_all();
所有权链

TargetList → vector → unique_ptr<Target> → 具体任务对象

  • TargetList 拥有任务

  • 容器析构时逐个 delete

  • 任务对象通过虚析构正确销毁

  • 调用方通过 std::move 明确移交所有权

对比裸指针版

不需要写 ~TargetList() { for (...) delete p; }；不会因为提前 return 或异常而泄漏。

课堂任务 14：把泄漏的程序改成智能指针
任务

下面这段代码存在泄漏与潜在 UAF：

class TargetList {
public:
    void add(Target* t) { targets_.push_back(t); }
    ~TargetList() { /* 没有 delete */ }
private:
    std::vector<Target*> targets_;
};

改造为：

  1. std::vector<std::unique_ptr<Target>>
  2. add(std::unique_ptr<Target>)，用 std::move 放入
  3. 删除手写析构函数
  4. 增加 run_all()，通过基类指针调用 run()
  5. 用 ASan 验证无泄漏、无 UAF
验收标准

  • TargetList 析构后 ASan 无泄漏报告

  • 不能从 TargetList 外部删除任务

  • 新增任务类型不需要修改 TargetList

  • 基类 Target 有虚析构函数

  • 不使用裸 new / delete

提示 add 的签名改为 void add(std::unique_ptr<Target> target)；调用方用 std::make_unique 构造，std::move 传入。
任务 14 参考实现 
#include <memory>
#include <utility>
#include <vector>
// 假设 Target/PrintTarget/CommandTarget 已定义

class TargetList {
public:
    void add(std::unique_ptr<Target> target) {
        targets_.push_back(std::move(target));
    }

    void run_all() const {
        for (const auto& t : targets_) {
            t->run();
        }
    }

    std::size_t size() const {
        return targets_.size();
    }

private:
    std::vector<std::unique_ptr<Target>> targets_;
};

int main() {
    TargetList list;
    list.add(std::make_unique<PrintTarget>("hello"));
    list.add(std::make_unique<CommandTarget>("g++ main.o -o app"));
    list.run_all();
}
要点

  • unique_ptr 独占所有权

  • std::move 明确移交

  • vector 析构自动释放所有任务

  • Target 的虚析构保证派生类析构执行

  • ASan 验证：g++ -fsanitize=address

不要

在 TargetList 外部保存任务的裸指针并继续使用；对象生命周期由 TargetList 拥有，外部只能“借用”。

常见陷阱

裸指针/资源

  • delete 后继续使用

  • 同一指针 delete 两次

  • 返回局部变量地址/引用

  • 异常路径忘记释放

  • 数组与标量 delete 混用

智能指针

  • 用同一裸指针构造多个 shared_ptr

  • shared_ptr 循环引用

  • unique_ptr 拷贝（编译错误）

  • std::move 后继续使用源指针

  • 基类析构非虚，unique_ptr<Base> 删除派生对象

  • 过度使用 shared_ptr（所有权不清晰）

选择顺序

栈对象/值语义 → unique_ptr → shared_ptr → 裸指针（仅借用）。shared_ptr 不是默认选择。

  • weak_ptr：观察

  • 裸指针/引用：借用

内存安全的核心不是“记得 delete”，而是让每个对象都有明确的所有者，并让类型系统替你检查。
